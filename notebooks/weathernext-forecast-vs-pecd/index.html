WeatherNext forecast capacity factors vs. PECD / ERA5¶

PECD’s own official capacity-factor product is good for two structural reasons that have nothing to do with weather-forecast skill: (1) a proprietary methodology built on real, per-turbine wind-farm data this hub doesn’t have access to, and (2) it is computed from ERA5 reanalysis -- essentially perfect, ex-post weather, not a forecast. forecast_capacity_factors_de (energy-data-hub) instead uses WeatherNext 3’s actual day-ahead/multi-day forecasts, run through this hub’s own from-scratch replication methodology (GWA wind-speed bias correction, hub-height extrapolation, per-plant turbine curves, PECD-documented solar chain) -- so it is missing both of PECD’s advantages at once: neither PECD’s own methodology, nor perfect hindsight weather.

This page asks, step by step: how big is the gap against PECD overall: how does that gap look over real time (not just as a summary number), and how much of it is attributable to weather-forecast uncertainty specifically (isolated by comparing against this hub’s own ERA5-based replication, same methodology, same real weather-observation basis) rather than to the methodology difference against PECD.

Known caveats carried over from the exploration that produced this page (see the OpenSpec change add-weathernext-forecast-capacity- factors and its own design notes for the fuller trail):

  • A forecast lead hour that happens to fall at night trivially gives zero solar capacity factor on both sides of any comparison -- not a bug, just means a single fixed lead hour is never a fair solar comparison point. Full RE’s blend is dominated by wind at those hours.

Everything this page reads is a materialized hub asset -- no inline CDS/BigQuery pulls, no inline weather-to-capacity-factor conversion. PECD’s pecd_*_capacity_factors assets now self-extend into the current year (2015-2025 frozen + however much of this year CDS has published, re-checked on every materialization -- see edh.pecd.download_current_ year_capacity_factor_zip), and the ERA5-fed comparison series comes from era5_capacity_factors_de (same per-plant replication methodology as forecast_capacity_factors_de, just fed real reanalysis instead of a forecast) -- this page only loads and plots both, it doesn’t compute either.

Today’s real fleet, and PECD’s own zone/region weights¶

Every comparison on this page blends PECD’s zone- or NUTS2-level product (and this hub’s own per-plant replication) up to one Germany number per technology using today’s real, pinned MaStR fleet as weights -- the same “current pinned snapshot” convention forecast_capacity_factors_de itself uses (see that asset’s own design notes on why this isn’t time-varying). expand_wind_zone_weights (wind, PEON/PEOF zones) and a straight per-(region, technology) capacity grouping (solar) are both already-validated hub functions, reused as-is.

def blend_to_national(wind_onshore_de: pd.DataFrame, wind_offshore_de: pd.DataFrame, solar_de_by_tech: dict) -> pd.DataFrame:
    """PECD's own zone/region-columned product (or this hub's matching
    replication output), blended to one Germany number per technology +
    a capacity-weighted `full_re` blend, using today's real fleet weights."""
    common_on = [z for z in onshore_weights.index if z in wind_onshore_de.columns]
    w_on = onshore_weights[common_on] / onshore_weights[common_on].sum()
    cf_onshore = (wind_onshore_de[common_on] * w_on).sum(axis=1)

    common_off = [z for z in offshore_weights.index if z in wind_offshore_de.columns]
    w_off = offshore_weights[common_off] / offshore_weights[common_off].sum()
    cf_offshore = (wind_offshore_de[common_off] * w_off).sum(axis=1)

    cf_pv = pd.Series(0.0, index=solar_de_by_tech["60"].index)
    weight_total = 0.0
    for (region, tech), weight in solar_weights.items():
        if region in solar_de_by_tech[tech].columns:
            cf_pv = cf_pv.add(solar_de_by_tech[tech][region] * weight, fill_value=0)
            weight_total += weight
    cf_pv = cf_pv / weight_total
    # PECD's documented solar-only 1h timestamp shift -- see edh.pecd.process_solar_capacity_factors.
    cf_pv.index = cf_pv.index - pd.Timedelta(hours=1)

    full_re = (cf_pv * cap_pv + cf_onshore * cap_onshore + cf_offshore * cap_offshore) / cap_total
    return pd.DataFrame({"pv": cf_pv, "wind_onshore": cf_onshore, "wind_offshore": cf_offshore, "full_re": full_re}).dropna(how="all")

WeatherNext forecasts, every init and lead hour on disk¶

forecast_capacity_factors_de’s own output, long format (one row per lead hour per technology per init day). Loaded once here and reused by every section below -- in particular, pivoted on the unique key (init_day, lead_hours) before anything else touches it: a naive pivot keyed only on valid_time would silently average together different lead hours that happen to land on the same real timestamp (a real bug caught while building this page’s lead-hour error curves the first time -- see the OpenSpec change’s design notes).

1. How does the forecast-based conversion do against PECD, by lead hour?¶

Mean Absolute Error, in capacity-factor units, between WeatherNext’s forecast (this hub’s own methodology) and PECD’s own product, for every lead hour -- many different (init day, lead hour) pairs legitimately land on the same real timestamp; each is scored against PECD’s single value at that timestamp independently (a correct many-to-one join, not an average).

def mae_by_lead_hour(forecast_wide: pd.DataFrame, reference_wide: pd.DataFrame, reference_label: str) -> pd.DataFrame:
    records = []
    for tech in ["pv", "wind_onshore", "wind_offshore", "full_re"]:
        merged = forecast_wide[["lead_hours", "valid_time", tech]].merge(
            reference_wide[[tech]].rename(columns={tech: f"{tech}_ref"}), left_on="valid_time", right_index=True, how="inner"
        )
        merged["err"] = merged[tech] - merged[f"{tech}_ref"]
        for lead, g in merged.groupby("lead_hours"):
            if len(g) < 5:
                continue
            records.append({"technology": tech, "lead_hours": lead, "n": len(g), "bias": g["err"].mean(), "mae": g["err"].abs().mean(), "rmse": np.sqrt((g["err"] ** 2).mean())})
    out = pd.DataFrame(records)
    out["reference"] = reference_label
    return out

3. At the shortest lead hour (minimal weather uncertainty): forecast vs. PECD, and vs. ERA5¶

Lead hour 1 is as close as WeatherNext gets to “no forecast uncertainty left” (there is no lead hour 0 in WeatherNext’s published product, confirmed live against BigQuery). Comparing at this lead hour against two different references isolates two different things: against ERA5 (same hub methodology on both sides) isolates the pure weather-data- basis difference; against PECD (PECD’s own methodology) mixes that same small weather difference with PECD’s own, much larger, methodology difference.

def scatter_grid(merged: pd.DataFrame, ref_suffix: str, ref_label: str, color: str, title: str):
    fig, axes = plt.subplots(1, 3, figsize=(13, 4.6), dpi=130)
    fig.patch.set_facecolor(SURFACE)
    for ax, tech in zip(axes, LEAD1_TECHS):
        ax.set_facecolor(SURFACE)
        ref, fc = merged[f"{tech}{ref_suffix}"], merged[tech]
        ax.scatter(ref, fc, s=36, color=color, alpha=0.85, edgecolor="white", linewidth=0.5, zorder=3)
        ax.plot([0, 1], [0, 1], linestyle=(0, (4, 3)), linewidth=1.3, color="#9a9890", zorder=1)
        ax.set_xlim(-0.03, 1.03)
        ax.set_ylim(-0.03, 1.03)
        ax.set_aspect("equal")
        ax.set_title(LABELS[tech], color=TEXT_PRIMARY, fontsize=11.5, loc="left")
        ax.grid(True, color="#e5e3dc", linewidth=0.7, zorder=0)
        for spine in ax.spines.values():
            spine.set_color("#d8d6cd")
        ax.tick_params(colors=TEXT_SECONDARY, labelsize=8.5)
    fig.suptitle(title, color=TEXT_PRIMARY, fontsize=13, x=0.02, ha="left", y=0.99)
    fig.supxlabel(f"{ref_label} capacity factor", color=TEXT_SECONDARY, fontsize=10.5)
    fig.supylabel("WeatherNext forecast, 1h lead", color=TEXT_SECONDARY, fontsize=10.5)
    fig.tight_layout(rect=[0.02, 0.02, 1, 0.9])
    plt.show()


def timeseries_grid(merged: pd.DataFrame, ref_suffix: str, ref_label: str, ref_color: str, title: str):
    fig, axes = plt.subplots(3, 1, figsize=(11, 10), dpi=130, sharex=True)

    plt.show()

3a. Same methodology (ERA5) -- isolates the pure weather-data-basis gap¶

Forecast and reference go through the identical conversion code here; the only thing that can differ is the weather input itself -- WeatherNext’s own 1h-lead analysis/initial-condition field vs. ERA5’s reanalysis. Whatever gap remains is attributable to that (and possibly a labeling convention, e.g. the kind of 1h accumulation/timestamp offset PECD’s own solar product is independently known to have -- not yet checked for WeatherNext itself).
